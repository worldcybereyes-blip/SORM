1. ABSTRACT
===========
SORM is the Russian abbreviation for System for Operative Investigative
Activities, a lawful interception framework in which telecom operators install
equipment that gives authorized agencies access to communications data.
Comparable frameworks exist elsewhere: CALEA in the United States, the ETSI
lawful interception standards in Europe, and the interception provisions of the
Telegraph Act and IT Act rules in India.

This project reproduces the technical shape of such a system as a safe,
self-contained simulation. It generates synthetic telecom traffic, mirrors it
through simulated passive hardware, inspects it with a Deep Packet Inspection
engine, extracts metadata, and stores it in a SQLite database that an analyst
can query from a terminal or a local web page.

Objectives:
  - Explain how passive taps mirror traffic without disturbing the live network
  - Show how DPI parses protocols and extracts metadata
  - Show why encryption limits content visibility to metadata only
  - Demonstrate indexed storage and search over large record sets
  - Show the oversight layer: roles, case references and a tamper-evident audit log
  - Provide a runnable portfolio project for networking and SOC learners

Scope: every packet, number, IP address and domain is fictional. No real
network interface is ever opened.


2. SYSTEM ARCHITECTURE
======================
The system is a linear pipeline of five stages:

  Telecom core (traffic generator)
        |
        v
  Network taps (optical splitter, network tap, passive probe)
        |
        v
  DPI engine (parse, extract, match, score)
        |
        v
  Metadata storage servers (SQLite)
        |
        v
  Analyst terminal (CLI and web dashboard)

Design principles:
  - Non-intrusion: the live path must never be modified or delayed by monitoring
  - Separation of duties: each module has a single responsibility
  - Metadata first: only metadata and flags are stored, not message content
  - Repeatability: a random seed makes every run reproducible
  - Zero dependencies: the standard library is enough

Module map:
  telecom_generator.py   produces Packet objects
  network_appliances.py  mirrors Packet copies to the probe
  dpi_engine.py          turns Packet copies into InspectionResult objects
  storage_server.py      persists and searches InspectionResult data
  access_control.py      login, roles, case references and the audit log
  main.py                wires the stages together and offers the menu


3. HARDWARE AND APPLIANCE LAYER
===============================

3.1 Optical splitter
--------------------
A passive optical splitter divides light from one fiber into two outputs with
a fixed power ratio, such as 90 percent to the live path and 10 percent to the
monitoring path. It needs no power and adds no processing delay.

The simulation computes a power budget in dBm:
  loss in dB = minus 10 times log10 of the power fraction, plus excess loss
  tap leg power = launch power minus fiber loss minus tap leg loss

With the defaults (launch minus 3 dBm, fiber loss 0.5 dB), a 90/10 split
leaves about minus 13.7 dBm on the tap leg. The probe receiver needs at least
minus 28 dBm. If the tap share is made very small, for example 0.1 percent,
the tap leg falls below sensitivity and mirrored copies are lost, while the
live leg is unaffected. This is shown with the option --tap-percent 0.1.

3.2 Network tap
---------------
A network tap aggregates the optical copy and presents it on a monitoring
port. The monitoring port has finite capacity. The simulation applies a bytes
per second limit using packet timestamps. When the limit is exceeded, the
mirrored copy is dropped and counted. The live packet is never blocked, which
is the defining property of a passive tap.

3.3 Passive probe
-----------------
The probe is the collection point. It only receives. It buffers mirrored
packets, counts them by protocol, and hands them to the DPI engine on drain.

3.4 Mirroring fabric and integrity check
----------------------------------------
TrafficMirroringFabric chains the three devices. Before mirroring, it takes a
SHA-256 fingerprint of the live packet. After mirroring it fingerprints the
forwarded packet again and compares. Any difference is counted as an integrity
failure. In a correct passive design this count is always zero, and the demo
output reports it.


4. DPI PROCESSING LOGIC
=======================

4.1 Input
---------
DPI works only on mirrored copies delivered by the probe.

4.2 Protocol parsing
--------------------
  SIP    : splits start line and headers, reads Via, From, To, Call-ID, CSeq
           and User-Agent, and extracts caller and callee from the SIP URIs
  SMS    : reads the pipe-delimited SMS log record: FROM, TO, STATUS and TEXT
  HTTP   : reads the request line and Host header; the host plus decoded path
           becomes searchable text
  HTTPS  : content is encrypted, so only TLS version, cipher and the SNI host
           name are visible; the text field stays empty on purpose
  IPDR   : reads subscriber, private and public IPs, NAT ports, destination,
           timestamps and byte counters

4.3 Metadata extraction
-----------------------
Each packet becomes one InspectionResult holding packet id, time, protocol,
caller, callee, source and destination IP and port, cell tower id, size, host,
a summary line, flags and a severity score.

4.4 Rules
---------
  KEYWORD           a watchlist keyword appears in inspectable text
  WATCH_DOMAIN      the host matches or is a subdomain of a watched domain
  WATCH_NUMBER      caller or callee is on the number watchlist
  WATCH_IP          source or destination falls in a watched address or range
  LARGE_RECORD      size is at or above the configured threshold
  SIP_INVITE_BURST  many INVITE messages from one source inside a time window,
                    tracked with a sliding window of timestamps

4.5 Severity scoring
--------------------
Each distinct rule type adds its weight from the configuration. The total is
capped at 100. Levels: INFO for 0, LOW below 30, MEDIUM below 60, HIGH above.

4.6 Configuration
-----------------
Rules live in config/watchlist.json. Edit that file to change keywords,
domains, numbers, networks, thresholds and weights without touching code.


5. STORAGE INFRASTRUCTURE
=========================

5.1 Database
------------
SQLite stores one table named metadata. Columns: id, packet_id, ts, ts_iso,
protocol, caller_id, callee_id, src_ip, dst_ip, src_port, dst_port,
cell_tower_id, packet_size, host, flags, severity, severity_level, summary.
The packet_id column is unique, so re-inserting the same record is ignored.

5.2 Indexes
-----------
Indexes exist on time, caller, callee, protocol and severity so common
searches stay fast as the table grows.

5.3 Search
----------
The search method builds its WHERE clause from the filters supplied and always
uses bound parameters, which prevents SQL injection. Filters: caller, callee,
party (either side), ip, protocol, tower, flag, minimum severity, keyword,
time range and limit.

5.4 Analyst terminal
--------------------
Commands: search, number, ip, alerts, stats, export, help, quit. Results are
printed as a fixed-width table and the last result set can be exported to CSV.

5.5 Web dashboard
-----------------
A small standard library HTTP server binds to 127.0.0.1 only. It shows summary
cards, a search form and a result table with rows shaded by severity. Every
value is HTML-escaped. The path /stats returns the statistics as JSON.

5.6 Access control and audit log
--------------------------------
All access to stored metadata goes through the AccessController class in
access_control.py. Nothing in the terminal or dashboard talks to the search
method directly.

Roles and separation of duties:
  ADMIN    manages users, runs the simulation, clears metadata, sees statistics
  ANALYST  searches and exports metadata, with a case reference
  AUDITOR  reads the audit log and verifies it
No role holds every permission. The person who administers accounts cannot read
records, and the person who reads records cannot read or alter the audit log.

Login:
  - Passwords are stored as salted PBKDF2-HMAC-SHA256 hashes, 200000 rounds
  - Comparison uses hmac.compare_digest, and unknown users cost the same time
  - Five failed logins lock the account until an admin unlocks it
  - Error messages are generic so they do not reveal which usernames exist
  - The dashboard uses HTTP Basic login and is bound to 127.0.0.1 only

Case references:
Searches and exports are refused unless a reference such as CASE-2026-001 is
supplied. It stands in for a warrant or authorization number. The simulation only
checks its format. A real system would validate it against a legal case system.

Audit log:
  - Records time, user, role, action, case reference, detail and outcome
  - Covers logins, failures, lockouts, denials, searches, exports, statistics,
    user changes, simulation runs, metadata clears and audit reads
  - Search entries store the filters used and the number of rows returned
  - Passwords are never logged and control characters are stripped from input
  - Each entry stores the SHA-256 hash of the previous entry, forming a chain
  - SQLite triggers reject UPDATE and DELETE on the audit table
  - The verify command recomputes the chain and reports the first broken entry

Known limit: the triggers can be dropped by anyone with raw file access, and a
chain alone cannot prove that the newest entries were not truncated. The hash
chain catches edits and mid-log deletions. For truncation, an auditor should note
the head hash printed by verify and compare it later, or ship entries to separate
write-once storage as production systems do.

5.7 Real-world note
-------------------
Production systems add encryption at rest, multi-person approval, retention limits,
independent log storage, hardware-backed credentials and live legal authorization
checks. These remain out of scope here.


6. STEP-BY-STEP CODE WALKTHROUGH
================================

6.1 build_sorm_project.py
-------------------------
Holds every file as a text block, checks that the two documents contain no
asterisk or hash characters, writes everything into a SORM folder, generates
sample datasets using the generator, and compiles each Python file to catch
syntax errors.

6.2 telecom_generator.py
------------------------
Step 1: the Packet dataclass defines the fields every module shares.
Step 2: the generator builds 25 fictional subscribers, each with a number, a
        private IP and a home cell tower.
Step 3: a simulated clock advances by a random interval per packet.
Step 4: generate_sip builds a complete SIP message with headers.
Step 5: generate_sms builds an SMS log record, with about 12 percent of
        messages containing sensitive demo phrases.
Step 6: generate_http builds a request; generate_https builds TLS metadata with
        an encrypted byte count; generate_ipdr builds a usage record.
Step 7: stream() mixes protocols by weight and sometimes injects a burst of
        ten INVITE messages from one subscriber.

6.3 network_appliances.py
-------------------------
Step 1: OpticalSplitter computes the power budget and returns a live packet
        plus a deep copy, or no copy if the tap leg is too weak.
Step 2: NetworkTap enforces the per-second mirror capacity.
Step 3: PassiveProbe stores copies and counts them.
Step 4: TrafficMirroringFabric.process runs the chain and verifies the
        fingerprint of the live packet did not change.

6.4 dpi_engine.py
-----------------
Step 1: load default rules and merge the JSON watchlist if present.
Step 2: choose the parser for the packet protocol.
Step 3: build the list of flags by applying each rule.
Step 4: compute the severity score and level.
Step 5: return an InspectionResult and update counters.

6.5 storage_server.py
---------------------
Step 1: open SQLite and create the schema and indexes.
Step 2: insert_many writes results in one transaction.
Step 3: search builds a safe parameterized query.
Step 4: stats aggregates counts by protocol, level, tower, caller and flag.
Step 5: analyst_cli and run_dashboard present the data.

6.6 main.py
-----------
Step 1: parse options.
Step 2: open the database, optionally clearing it.
Step 3: run_simulation executes the four stages and prints a report per stage.
Step 4: show_summary prints statistics and the top alerts.
Step 5: menu offers repeated runs, the terminal, the dashboard, export and
        clear.

6.7 access_control.py
---------------------
Step 1: AUTH_SCHEMA creates the users table and the audit table with two
        append-only triggers.
Step 2: seed_demo_users creates the three demo accounts on first run.
Step 3: authenticate hashes the password, compares in constant time, counts
        failures and locks the account at five.
Step 4: authorize checks the role permission and, for search and export, the
        case reference format. Every denial is logged.
Step 5: search, stats, export, user management and clear_metadata each call
        authorize first and write an audit entry after acting.
Step 6: log appends an entry whose hash covers the previous entry hash.
Step 7: verify_audit recomputes the chain from the start.
main.py logs in before showing a role-specific menu, and the terminal and
dashboard in storage_server.py call the controller instead of the database.

7. WINDOWS EXECUTION GUIDE
==========================

Requirements: Windows 10 or Windows 11, Python 3.8 or newer.

Option A: one click
  1. Install Python from python.org and tick Add python.exe to PATH
  2. Open the SORM folder in File Explorer
  3. Double-click run_windows.bat

What the batch file does:
  Step 1: looks for the py launcher, then python, and tests that it really runs
  Step 2: verifies the version is 3.8 or newer
  Step 3: creates a virtual environment in the .venv folder if missing
  Step 4: activates it and installs requirements.txt (nothing external needed)
  Step 5: starts main.py and keeps the window open when it ends

Option B: manual
  1. Open Command Prompt in the SORM folder
  2. py -3 -m venv .venv
  3. .venv\Scripts\activate
  4. python main.py --demo

Useful runs:
  python main.py --demo --packets 1000 --seed 7
  python main.py --demo --tap-percent 0.1
  python main.py --user analyst1 --cli
  python main.py --user auditor1 --cli
  python main.py --dashboard --port 8080

Logins: the first run creates admin, analyst1 and auditor1. Their demo passwords
are listed in README.txt under ACCESS CONTROL AND AUDIT. The password is always
typed at a prompt and never shown on screen.

Troubleshooting:
  - Python not recognized: reinstall and tick Add python.exe to PATH
  - Port already in use: pass a different value with --port
  - Garbled characters: the output is plain ASCII, so use Command Prompt
    or Windows Terminal


8. LIMITATIONS AND ETHICAL SCOPE
================================
  - Packets are simplified Python objects, not real network frames
  - No real SS7, Diameter, RADIUS or IMS stacks are implemented
  - Single-threaded, single machine, no high availability
  - Demo passwords are public and case references are only format-checked
  - The audit log lives in the same database file as the data
  - The project teaches architecture and defensive understanding. It must not
    be pointed at real traffic or real people. Real interception is lawful only
    with proper authorization and oversight.
